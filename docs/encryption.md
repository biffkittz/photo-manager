# Encryption

All photos are encrypted at rest, everywhere: in Wasabi (archive), in Blob Storage (staging, renditions,
downloads) and in Temporal Cloud (payloads). This document is the normative specification of the formats;
the implementation is `app/backend/src/PhotoManager.Core/Crypto` and is covered by `PhotoManager.Core.Tests`.

## Legacy format (`protect.ps1`), read-only

Every object written by `protect.ps1` (`yyyy-MM-dd/<name>.encrypted`):

```
offset 0   salt  32 bytes  random
offset 32  iv    16 bytes  random
offset 48  ciphertext      AES-256-CBC, PKCS7 padding
key = PBKDF2-HMAC-SHA1(password as UTF-8, salt, 10 000 iterations, 32 bytes)
```

This is exactly `Rfc2898DeriveBytes(password, salt, 10000)` (which defaults to SHA-1 and UTF-8) as used by
`Encrypt-FileBytes` / `Decrypt-FileBytes`. Compatibility is proven both ways by tests: fixtures generated by
running the real `protect.ps1` functions in PowerShell are decrypted by the app, and files the app writes in
this format are decrypted by `protect.ps1` (`TestData/Legacy/generate-vectors.ps1`).

Weaknesses (why new files use v2): no integrity protection (tampering is detected only if it breaks the
padding), SHA-1 with a low iteration count. The app never writes this format; `photo-crypt encrypt --legacy`
exists only as an escape hatch.

## v2 format (new uploads, renditions, staging, downloads)

```
header (80 bytes, all integers big-endian)
  0   magic            8   89 50 4D 56 32 0D 0A 1A   ("\x89PMV2\r\n\x1A")
  8   version          1   2
  9   key type         1   1 = password (PBKDF2), 2 = raw 256-bit key
  10  reserved         2   must be zero
  12  chunk size       4   plaintext bytes per chunk (1 KiB to 16 MiB; default 64 KiB)
  16  kdf iterations   4   PBKDF2 iterations (100 000 to 2 000 000) for type 1, else 0
  20  key id           8   first 8 bytes of HMAC-SHA256(master key, "photo-manager/v2/key-id")
  28  kdf salt         16  PBKDF2 salt (type 1), zeros for type 2
  44  file salt        32  random per file
  76  metadata length  4   length of the sealed metadata incl. tag (0 = none, max 64 KiB + 16)
metadata (optional)    AES-256-GCM(metadata key, nonce = 12 zero bytes, UTF-8 JSON, aad = header)
chunks                 AES-256-GCM(content key, nonce_i, plaintext chunk i) = ciphertext || 16-byte tag
```

Key derivation:

```
master key   = PBKDF2-HMAC-SHA256(password, kdf salt, iterations, 32)   (type 1, archive)
             = the raw web key                                          (type 2)
prk          = HKDF-Extract(SHA-256, salt = file salt, ikm = master key)
content key  = HKDF-Expand(prk, "photo-manager/v2/content"  || header, 32)
metadata key = HKDF-Expand(prk, "photo-manager/v2/metadata" || header, 32)
nonce_i      = 00 00 00 || uint64_be(i) || final flag (01 for the last chunk, else 00)
```

Design rationale:

- **Per-file keys** (random 256-bit file salt) make counter nonces safe: no key ever encrypts two files.
- **The whole header is bound into the keys** through the HKDF `info`, so any header modification breaks
  authentication of the metadata and of every chunk.
- **Chunk index and final flag in the nonce** (the STREAM construction) detect reordered, dropped, truncated
  or appended chunks. Every chunk is authenticated before any of its plaintext is released.
- **Streaming**: encryption and decryption use bounded memory; the encryptor seals a full chunk as non-final
  only when more data arrives, and disposing an encryptor without `CompleteAsync` deliberately leaves an
  invalid file rather than a valid-looking truncated one.
- **Key id** lets a reader pick the right key during rotation and fail fast with a clear error.
- **Bounded KDF parameters** stop a crafted header from forcing an expensive PBKDF2 computation, and readers
  state the key type they expect, which is checked against the header *before* any key is resolved: web-key
  data can never trigger an archive-password derivation, and password-derived keys are cached only when they
  match a genuine file.

The archive KDF salt is a constant per deployment (default: first 16 bytes of
`SHA-256("photo-manager/archive-kdf-salt/v1")`, base64 `O1zP6nn3EyFZaMO35BZ02g==`), so the 600 000-iteration
PBKDF2 runs once per worker process; it is recorded in every header, so changing it later breaks nothing.

### Embedded metadata

Archive files carry sealed JSON metadata (`EmbeddedPhotoMetadata`): photo id, original filename, content type,
size, SHA-256, AI description and tags, capture date, upload date and uploader. The bucket is therefore
self-describing: re-indexing a bucket into an empty database recovers names and descriptions of every v2 file.
Object keys (`v2/yyyy/MM/<photo id>.pmv2`) reveal nothing about content.

## Where each key is used

| Data | Location | Format | Key |
|---|---|---|---|
| Existing archive | Wasabi `yyyy-MM-dd/*.encrypted` | legacy | archive password |
| New originals | Wasabi `v2/yyyy/MM/*.pmv2` | v2 type 1 | archive password |
| Staged uploads | Blob `staging/<id>` (deleted after ingest, lifecycle 1 day) | v2 type 2 | web key |
| Thumbnails/previews | Blob `renditions/<id>/{thumbnail,preview}` | v2 type 2 | web key |
| Prepared downloads | Blob `downloads/<id>` (lifecycle 1 day) | v2 type 2 | web key |
| Temporal payloads | Temporal Cloud | AES-256-GCM codec (random nonce, key id in metadata; unencrypted payloads are rejected) | payload key |
| Cookies | Browser | ASP.NET Core Data Protection | key ring wrapped by Key Vault RSA key |

Plaintext photos exist only in worker memory (buffers are zeroed after use) and in the response stream to
the signed-in user. Archive re-encryption stages **ciphertext** on the worker's temporary disk to compute
Content-MD5 for the upload.

## Rotation

See [operations.md](operations.md#rotating-keys). In short: the web key and payload key support a
`...Previous` value (decrypt-only) for zero-downtime rotation. The archive password is the root of the whole
archive (including `protect.ps1` history); rotating it means re-encrypting every object and is a deliberate,
separate project.

## Offline tool

`photo-crypt` (`app/backend/src/PhotoManager.Cli`) reads every format with only the password (and, for
web-key data, the web key), so the archive never depends on the app being deployed:

```bash
cd app/backend
dotnet run --project src/PhotoManager.Cli -- inspect  file.pmv2
dotnet run --project src/PhotoManager.Cli -- metadata file.pmv2
dotnet run --project src/PhotoManager.Cli -- decrypt  file.pmv2 photo.jpg         # or a legacy .encrypted file
dotnet run --project src/PhotoManager.Cli -- encrypt  photo.jpg file.pmv2 [--legacy]
```

Secrets come from `PHOTO_CRYPT_PASSWORD` / `PHOTO_CRYPT_WEB_KEY` or a hidden prompt, never from arguments.
